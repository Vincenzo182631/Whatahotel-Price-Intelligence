# 08 — MVP User Interface

Covers proposal request 9: the exact information the customer sees. This document specifies *information*, not visual design.

---

## 1. Principle

> The customer should leave knowing three things: **what it costs**, **whether that's good**, and **how sure we are**.

Everything below serves one of those. Anything that serves none of them does not belong in the MVP.

The second and third are inseparable. Showing a Deal Score without its confidence is the single easiest way to mislead someone, and it is why confidence appears at the same level of prominence as the score rather than in a footnote.

---

## 2. Screen structure

```
┌──────────────────────────────────────────────────────────┐
│  A · SUBJECT      hotel · room · dates · guests · terms   │
├──────────────────────────────────────────────────────────┤
│  B · PRICE        $689/night · $2,067 total · effective   │
├──────────────────────────────────────────────────────────┤
│  C · VERDICT      Deal Score 91 · Confidence 88 · BOOK NOW│
├──────────────────────────────────────────────────────────┤
│  D · EXPLANATION  one short paragraph                     │
├──────────────────────────────────────────────────────────┤
│  E · REASONS      3–5 bullet facts                        │
├──────────────────────────────────────────────────────────┤
│  F · HISTORY      chart · 30 / 60 / 90 day toggle         │
├──────────────────────────────────────────────────────────┤
│  G · STATS        typical · lowest · highest · percentile │
├──────────────────────────────────────────────────────────┤
│  H · PROVENANCE   data timestamp · observation count      │
├──────────────────────────────────────────────────────────┤
│  I · ACTION       Book · Talk to a Lorraine Travel advisor│
└──────────────────────────────────────────────────────────┘
```

A, B, C and H are mandatory in every state, including `INSUFFICIENT_DATA`.

## 3. Required elements

### A · Subject — *what exactly is being priced*

Hotel name · room type name · check-in–check-out with night count · guest count · **rate terms** (e.g. "Breakfast included · Free cancellation").

Rate terms are mandatory, not optional detail. The entire scoring model rests on comparing like with like (doc 01 §4); if the customer cannot see which product was assessed, they cannot tell whether the assessment applies to the rate they are about to book.

If the room type was auto-selected rather than chosen, say so: *"Showing the lowest available rate: Ocean View King. Change room."*

### B · Current price

- **Nightly rate**, largest monetary element — this is what travelers compare
- **Total for the stay**, adjacent and clearly labelled with night count
- **Tax basis**, explicit: "Includes taxes and fees" or "Before taxes and fees". Never ambiguous
- **Effective rate** when benefits exist (F6): *"Effective $659/night after $30/night in included benefits"* with a hover/expand listing the benefits and their valuations

### C · Verdict — three elements, equal footing

**Deal Score** — number 0–100 plus band label ("Excellent rate"). The label carries the meaning; the number carries the precision.

**Confidence** — number 0–100 plus band label ("High confidence"). Never buried, never a tooltip-only element.
Plain-language definition available inline: *"How much price history we have for this exact room and dates."*

**Recommendation** — one of four, with a fixed label and a one-line rationale:

| Value | Label | Sub-line |
|---|---|---|
| `BOOK_NOW` | **Book now** | "This rate is unusually good and rising." (G3) / "This rate is well below typical." (G2) |
| `WAIT` | **Consider waiting** | "This rate is above typical and hasn't been rising." |
| `CONSIDER` | **Worth considering** | "This rate is about normal for this room." |
| `INSUFFICIENT_DATA` | **Not enough data yet** | "We're still building price history for this room." |

Note the WAIT label is *"Consider waiting"*, not *"Wait"*. The softer wording is deliberate: it is a recommendation under uncertainty, and the language should not exceed the confidence behind it.

**Decision D4 — presentation at low confidence.** Recommended behaviour:

| Confidence band | Deal Score shown as |
|---|---|
| HIGH (75+) | Number + band label |
| MODERATE (55–74) | Number + band label + caveat line |
| LOW (40–54) | **Band label only, no number** |
| INSUFFICIENT | No score at all |

A precise-looking "83" backed by eleven observations invites more trust than the evidence supports. The band label conveys everything we actually know at that confidence level.

### D · Explanation

One paragraph, maximum three sentences, from the explanation engine (doc 04). Rendered identically whether it came from the model or the template — the customer should never be able to tell, and there is no "AI" badge, because the *facts* are not AI-generated and labelling them as such would misrepresent their provenance.

### E · Key reasons

3–5 bullets, strongest first, each a single fact with a direction indicator:

- ↓ 7.9% below the typical rate for this room
- ↓ 8% below 6 comparable hotels for these dates
- ↑ Rate has risen 9% in the past 7 days
- ✓ Includes breakfast for 2 and a $100 hotel credit

**Negative reasons are shown with equal prominence.** Suppressing them would make the score unexplainable whenever it is low, and the product's entire value proposition is being trusted.

### F · Price history

Line chart of the same-stay series, with 30 / 60 / 90-day toggle (default 90, matching the proposal).

- Current price marked distinctly
- Typical (median) shown as a reference line, labelled
- p10–p90 band shaded to show the normal range
- **Gaps are drawn as breaks in the line, never interpolated** — see doc 06 §3. A continuous line across days we never observed would be fabricated history
- Sparse regions visually de-emphasized (thinner stroke or point-only rendering)
- Below the chart: 30/60/90-day change percentages

Accessible fallback: a data table with the same values, and a text summary of direction and magnitude. The chart must never be the sole carrier of information.

### G · Historical statistics

Matching the proposal's panel, with one correction:

| Label | Value | Note |
|---|---|---|
| Typical rate (90 days) | $748 | **Median**, not mean — labelled "typical", not "average" (doc 01 §6) |
| Lowest observed | $621 | |
| Highest observed | $925 | |
| This rate ranks | Cheaper than 91% of observed rates | The Deal Score in plain language |

### H · Provenance — *mandatory in every state*

- **"Rate observed 14 minutes ago"** — relative time, with exact timestamp on hover
- **"Based on 84 recorded rates over 90 days"** — the evidence base, in one line
- Any active caveats, plainly worded:
  - *"We're comparing against similar rooms at this hotel, not this exact room type."* (L4)
  - *"This room's price has been unusually volatile."* (high volatility)
  - *"Based on a limited number of recorded rates."* (thin baseline)

This block is what makes the product honest. It is also what makes it defensible if a customer disputes a recommendation.

### I · Action

Primary CTA: **Book this rate** (into the existing WhataHotel booking flow).
Secondary CTA: **Talk to a Lorraine Travel advisor** — the proposal's lead-generation path (§6), carrying the analysis context so the advisor opens the conversation already knowing the hotel, dates and assessment.

Phase 2 placeholder, not built in MVP: **Alert me if the price drops**.

## 4. Required states

| State | Behaviour |
|---|---|
| **Loading** | Skeleton; never a partial verdict. A score that renders before its confidence would be read and acted on |
| **Scored** | Full layout above |
| **`INSUFFICIENT_DATA`** | A, B, H, I only. C shows "Not enough data yet" with the reason. **No score, no empty gauge, no zero.** Phase-2 offer: "We'll keep tracking this — get notified when we can assess it" |
| **No current rate (409)** | Show hotel and dates; state the room is unavailable for these dates; offer nearby dates |
| **Stale data** | If the rate is older than `MAX_CURRENT_AGE_HOURS`, show the age prominently and suppress the recommendation |
| **Upstream error (503)** | Plain message, retry affordance. Never a fabricated or last-known score presented as current |

## 5. Presentation rules

1. **Never show a Deal Score without its confidence.** The one rule that, if broken, makes the product misleading.
2. **Never show `0` for an absent score.** Absence is `null` and renders as text.
3. **Never imply prediction.** No "prices will rise", no forecast arrow. MVP describes what has happened; it does not forecast (doc 04, validator V3).
4. **Never colour-code alone.** Every score band carries a text label — colour is redundant reinforcement, for accessibility and for greyscale/print.
5. **Round consistently.** Prices to the whole currency unit; percentages to one decimal below 10% and whole numbers above; scores to integers. A figure must read identically everywhere it appears on the page.
6. **State the currency** on the first monetary value and wherever ambiguity is possible.
7. **Relative timestamps with absolute on hover.** "14 minutes ago" is what people parse; the exact time is what they need in a dispute.

## 6. Embedding

Delivered as a self-contained widget mounted into an existing whatahotel.com page (U18 — the host platform is unknown to me, so the integration mechanism is provisional):

- Single script tag + mount element, or an iframe if style isolation is required
- Reads hotel/date context from the host page or from explicit parameters
- Style tokens (typography, colour, radius) injectable so it inherits WhataHotel's design language
- Fails silently and invisibly if the API is unreachable — a broken widget must never break the booking page it sits on
- Server-rendered variant required for Phase 5 SEO pages; the same components should support both, which is why doc 09 specifies an SSR-capable framework
