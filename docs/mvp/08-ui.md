# 08 — MVP User Interface

Covers proposal request 9: the exact information the customer sees. This document specifies _information_, not visual design.

---

## 1. Principle

> The customer should leave knowing three things: **what it costs**, **whether that's good**, and **how sure we are**.

Everything below serves one of those. Anything that serves none of them does not belong in the MVP.

The second and third are inseparable. Showing a Deal Score without its confidence is the single easiest way to mislead someone, and it is why confidence appears at the same level of prominence as the score rather than in a footnote.

---

## 2. Screen structure

```
┌──────────────────────────────────────────────────────────┐
│  A · SUBJECT      hotel · room · dates · guests · terms   │
├──────────────────────────────────────────────────────────┤
│  B · PRICE        $689/night · $2,067 total · effective   │
├──────────────────────────────────────────────────────────┤
│  C · VERDICT      Deal Score 91 · Confidence 88 · BOOK NOW│
├──────────────────────────────────────────────────────────┤
│  D · EXPLANATION  one short paragraph                     │
├──────────────────────────────────────────────────────────┤
│  E · REASONS      3–5 bullet facts                        │
├──────────────────────────────────────────────────────────┤
│  F · HISTORY      chart · 30 / 60 / 90 day toggle         │
├──────────────────────────────────────────────────────────┤
│  G · STATS        typical · lowest · highest · percentile │
├──────────────────────────────────────────────────────────┤
│  H · PROVENANCE   data timestamp · observation count      │
├──────────────────────────────────────────────────────────┤
│  I · ACTION       Book · Talk to a Lorraine Travel advisor│
└──────────────────────────────────────────────────────────┘
```

A, B, C and H are mandatory in every state, including `INSUFFICIENT_DATA`.

## 3. Required elements

### A · Subject — _what exactly is being priced_

Hotel name · room type name · check-in–check-out with night count · guest count · **rate terms** (e.g. "Breakfast included · Free cancellation").

Rate terms are mandatory, not optional detail. The entire scoring model rests on comparing like with like (doc 01 §4); if the customer cannot see which product was assessed, they cannot tell whether the assessment applies to the rate they are about to book.

If the room type was auto-selected rather than chosen, say so: _"Showing the lowest available rate: Ocean View King. Change room."_

### B · Current price

- **Nightly rate**, largest monetary element — this is what travelers compare
- **Total for the stay**, adjacent and clearly labelled with night count
- **Tax basis**, explicit: "Includes taxes and fees" or "Before taxes and fees". Never ambiguous
- **Effective rate** when benefits exist (F6): _"Effective $659/night after $30/night in included benefits"_ with a hover/expand listing the benefits and their valuations

### C · Verdict — three elements, equal footing

**Deal Score** — number 0–100 plus band label ("Excellent rate"). The label carries the meaning; the number carries the precision.

**Confidence** — number 0–100 plus band label ("High confidence"). Never buried, never a tooltip-only element.
Plain-language definition available inline: _"How much price history we have for this exact room and dates."_

**Recommendation** — one of four, with a fixed label and a one-line rationale:

| Value                                                                   | Label                   | Sub-line                                                                                 |
| ----------------------------------------------------------------------- | ----------------------- | ---------------------------------------------------------------------------------------- |
| `BOOK_NOW`                                                              | **Book now**            | "This rate is unusually good and rising." (G3) / "This rate is well below typical." (G2) |
| _(`WAIT` retired in config v4 — these inputs now render as `CONSIDER`)_ |
| `CONSIDER`                                                              | **Worth considering**   | "This rate is about normal for this room."                                               |
| `INSUFFICIENT_DATA`                                                     | **Not enough data yet** | "We're still building price history for this room."                                      |

The `WAIT` label used to read _"Consider waiting"_ rather than _"Wait"_, on the grounds that the language should not exceed the confidence behind it. Config v4 took that argument to its conclusion and removed the verdict: no wording is soft enough for a price forecast the data cannot support.

**Decision D4 — presentation at low confidence.** Recommended behaviour:

| Confidence band  | Deal Score shown as               |
| ---------------- | --------------------------------- |
| HIGH (75+)       | Number + band label               |
| MODERATE (55–74) | Number + band label + caveat line |
| LOW (40–54)      | **Band label only, no number**    |
| INSUFFICIENT     | No score at all                   |

A precise-looking "83" backed by eleven observations invites more trust than the evidence supports. The band label conveys everything we actually know at that confidence level.

### C2 · Verdict — the live-market model

`mount()` defaults to the live model (`/api/v1/live-intelligence`). It needs no accrued history, so it answers on a hotel we started collecting last week where the history model returns `INSUFFICIENT_DATA` for roughly a fortnight.

Same three elements on the same equal footing, different vocabulary:

**Deal Score** — the customer-facing figure is **0.0–10.0**, always to one decimal. The API returns both it and the underlying 0–100; the widget renders the one it is given rather than dividing, so a rounding rule cannot drift out of step with the bands.

| Band          | Label                 | Score   |
| ------------- | --------------------- | ------- |
| `EXCEPTIONAL` | **Exceptional value** | 8.5–10  |
| `STRONG`      | **Strong value**      | 7.0–8.4 |
| `MARKET`      | **Market rate**       | 5.0–6.9 |
| `PREMIUM`     | **Premium pricing**   | 0–4.9   |

**Confidence** — a word, not a number: HIGH / MEDIUM / LOW. A two-decimal confidence would invite a precision the inputs do not support, and the customer needs to tell an 8.7 backed by a full comp set from an 8.7 backed by three hotels at a glance.

**Verdict** — one of four. None of them is a wait:

| Value                   | Label                     | Sub-line                                                         |
| ----------------------- | ------------------------- | ---------------------------------------------------------------- |
| `BOOK_NOW`              | **Book now**              | "A strong rate against the market as it stands today."           |
| `BOOK_CONSIDER`         | **Consider booking**      | "A fair rate for this room against comparable hotels and dates." |
| `CONSIDER_ALTERNATIVES` | **Consider alternatives** | "Priced above comparable hotels, or above nearby dates."         |
| `NOT_ENOUGH_DATA`       | **Not enough data yet**   | "We do not have enough live rates to assess this stay yet."      |

Low confidence softens `BOOK_NOW` to `BOOK_CONSIDER` rather than reversing it. There is no state that recommends holding off, because holding off is a bet on a future price.

The disclosure (G2) carries one row per signal — comparable hotels, nearby dates, market availability — each showing its share of the score and the count behind it. **An excluded signal shows "excluded" and says why**, never a middling value: a signal displayed at the midpoint because nothing was known is indistinguishable from one measured there, which is rule 2 in a different costume.

Provenance (H) closes with the product's central claim and its central limit in one sentence: _"We compare rates that are live right now. We do not forecast future prices."_ It is not marketing copy and must not be trimmed for space.

### D · Explanation

One paragraph, maximum three sentences, from the explanation engine (doc 04). Rendered identically whether it came from the model or the template — the customer should never be able to tell, and there is no "AI" badge, because the _facts_ are not AI-generated and labelling them as such would misrepresent their provenance.

### E · Key reasons

3–5 bullets, strongest first, each a single fact with a direction indicator:

- ↓ 7.9% below the typical rate for this room
- ↓ 8% below 6 comparable hotels for these dates
- ↑ Rate has risen 9% in the past 7 days
- ✓ Includes breakfast for 2 and a $100 hotel credit

**Negative reasons are shown with equal prominence.** Suppressing them would make the score unexplainable whenever it is low, and the product's entire value proposition is being trusted.

### F · Price history

Line chart of the same-stay series, with 30 / 60 / 90-day toggle (default 90, matching the proposal).

- Current price marked distinctly
- Typical (median) shown as a reference line, labelled
- p10–p90 band shaded to show the normal range
- **Gaps are drawn as breaks in the line, never interpolated** — see doc 06 §3. A continuous line across days we never observed would be fabricated history
- Sparse regions visually de-emphasized (thinner stroke or point-only rendering)
- Below the chart: 30/60/90-day change percentages

Accessible fallback: a data table with the same values, and a text summary of direction and magnitude. The chart must never be the sole carrier of information.

### G · Historical statistics

Matching the proposal's panel, with one correction:

| Label                  | Value                              | Note                                                                 |
| ---------------------- | ---------------------------------- | -------------------------------------------------------------------- |
| Typical rate (90 days) | $748                               | **Median**, not mean — labelled "typical", not "average" (doc 01 §6) |
| Lowest observed        | $621                               |                                                                      |
| Highest observed       | $925                               |                                                                      |
| This rate ranks        | Cheaper than 91% of observed rates | The Deal Score in plain language                                     |

### G2 · Progressive disclosure

The widget is **collapsed by default**. Always visible: subject, price, effective
price, both scores, the verdict, the explanation sentence, the full provenance
block including every caveat, and the actions. Behind a single disclosure: the
WHY bullets, the price-history chart, and the comparison panel.

This is not a cosmetic preference. Embedded in a hotel page with everything
inline, the widget ran taller than the room card it describes and pushed the
remaining rooms roughly three screens down on mobile — a price analysis that
buries the booking flow works against the thing it exists to support. Measured
on the example page, collapsing cuts the widget from 1,592px to 930px on
desktop and from 2,273px to 1,448px on mobile, and the host page as a whole
from ~5,600px to ~2,270px.

**Provenance and caveats are deliberately outside the disclosure** — see §H.
Saving space by hiding the honesty block would be trading the wrong thing.

A host page with room to spare can pass `expanded: true` to `mount()`.

### H · Provenance — _mandatory in every state_

- **"Rate observed 14 minutes ago"** — relative time, with exact timestamp on hover
- **"Based on 84 recorded rates over 90 days"** — the evidence base, in one line
- Any active caveats, plainly worded:
  - _"We're comparing against similar rooms at this hotel, not this exact room type."_ (L4)
  - _"This room's price has been unusually volatile."_ (high volatility)
  - _"Based on a limited number of recorded rates."_ (thin baseline)

This block is what makes the product honest. It is also what makes it defensible if a customer disputes a recommendation.

### I · Action

Primary CTA: **Book this rate** (into the existing WhataHotel booking flow).
Secondary CTA: **Talk to a Lorraine Travel advisor** — the proposal's lead-generation path (§6), carrying the analysis context so the advisor opens the conversation already knowing the hotel, dates and assessment.

Phase 2 placeholder, not built in MVP: **Alert me if the price drops**.

## 4. Required states

| State                     | Behaviour                                                                                                                                                                             |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Loading**               | Skeleton; never a partial verdict. A score that renders before its confidence would be read and acted on                                                                              |
| **Scored**                | Full layout above                                                                                                                                                                     |
| **`INSUFFICIENT_DATA`**   | A, B, H, I only. C shows "Not enough data yet" with the reason. **No score, no empty gauge, no zero.** Phase-2 offer: "We'll keep tracking this — get notified when we can assess it" |
| **No current rate (409)** | Show hotel and dates; state the room is unavailable for these dates; offer nearby dates                                                                                               |
| **Stale data**            | If the rate is older than `MAX_CURRENT_AGE_HOURS`, show the age prominently and suppress the recommendation                                                                           |
| **Upstream error (503)**  | Plain message, retry affordance. Never a fabricated or last-known score presented as current                                                                                          |

## 5. Presentation rules

1. **Never show a Deal Score without its confidence.** The one rule that, if broken, makes the product misleading.
2. **Never show `0` for an absent score.** Absence is `null` and renders as text.
3. **Never imply prediction.** No "prices will rise", no "book before it goes up", no forecast arrow. The history model describes what has happened; the live model describes what is true right now. Neither forecasts (doc 04, validator V3; invariant P11).
4. **Never colour-code alone.** Every score band carries a text label — colour is redundant reinforcement, for accessibility and for greyscale/print.
5. **Round consistently.** Prices to the whole currency unit; percentages to one decimal below 10% and whole numbers above; history scores to integers; the live 0–10 figure always to one decimal, so 4 renders as "4.0". A figure must read identically everywhere it appears on the page.
6. **State the currency** on the first monetary value and wherever ambiguity is possible.
7. **Relative timestamps with absolute on hover.** "14 minutes ago" is what people parse; the exact time is what they need in a dispute.

## 6. Embedding

Delivered as a self-contained widget mounted into an existing whatahotel.com page (U18 — the host platform is unknown to me, so the integration mechanism is provisional):

- Single script tag + mount element, or an iframe if style isolation is required
- Reads hotel/date context from the host page or from explicit parameters
- Style tokens (typography, colour, radius) injectable so it inherits WhataHotel's design language
- Fails silently and invisibly if the API is unreachable — a broken widget must never break the booking page it sits on
- Server-rendered variant required for Phase 5 SEO pages; the same components should support both, which is why doc 09 specifies an SSR-capable framework

## Hotel Value mode (2026-08-26)

When the live response carries `intelligence_mode: "HOTEL_VALUE"` (no Deal
Score — the market comparison could not stand one), the widget does not render
a score tile, a confidence tile, or any sentence about data. It renders the
**hotel value** presentation instead: the verified Google rating as the lead
metric, the server-computed hotel-value headline in the verdict slot, and the
existing WHY YOU MIGHT CHOOSE THIS HOTEL section carrying the evidence — the
rating, review themes, perks, and the validated summary. The workings drawer
("How we worked this out") is suppressed: with no comparison, its rows could
only narrate what is missing. The premium box renders only when a premium was
actually measured (`premium_pct` non-null).

What this mode never does: invent a score (rule 3 — the score stays null),
fabricate evidence (the hotel-value layer's validators are unchanged), or
weaken the market engine (a scored response renders exactly as before). The
line between the modes is the same line the engine draws — `minWeightCoverage`
— presented as two products instead of one product and one apology.
